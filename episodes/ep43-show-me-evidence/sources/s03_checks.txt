（注意：Ping 沒有個人經歷；原文的「我」是報告的作者，要說「這份報告的作者」「這份報告說」。原文標「推算」「推論」「我的讀法」「自報」的地方要照說。技術名詞第一次出現時中英一起說（PR，合併請求；lint，自動檢查程式寫法的工具；AGENTS.md，寫給 agent 看的規則檔），之後擇一。不要用「你猜怎麼著」，「你猜」「你知道嗎」全集最多兩三次。每段結尾的小問題或轉折要保留。不加個人反應。）

花園。agent 的產出取決於輸入，程式庫是最大的輸入之一。2024 年她要審三個同事的 PR，現在大約是 300 個。限制和護欄是水泥地基，新寫的程式繞著它長。權宜寫法和反模式是害蟲，過時的技術也是。下一個 agent 會把它們當成慣例照抄，很快就爬滿整片。
三個例子。都來自 Grok Bot 用的 Electron 框架 Dune。
  React 的 useEffect 在產品程式碼裡禁用，只有框架內部能用。她的理由是「anything that requires nuance to use well often leads to slop」。這一類錯從此不會出現，審查的人也就不用再抓。
  最上層分成 electron/main 和 electron/renderer 兩個目錄，用相依圖分析和 lint 擋住互相匯入。這是 Cursor 時期學到的：agent 常把主程序的程式拉進畫面那邊，造成卡頓。
  Cursor 時期，agent 很愛拿計時器修問題，每個計時器旁邊都寫一段註解說明為什麼，結果計時器到處都是。Grok Bot 乾脆禁掉約 99% 的註解，因為註解會過時，也沒辦法強制。改成 lint 規則，錯誤訊息直接叫 agent 去修根本原因。
驗證。每一次糾正都變成一條確定性的檢查，審查要看的東西就越來越少。她說程式審查已經縮成看驗證產出，例如影片和截圖，還有形式化驗證的結果。他們用 TLA+ 檢查跨裝置的通知流程，用 Lean 檢查自己寫的 virtualization 程式庫會不會閃爍或抖動，用 Bombadil 做 UI 的 property-based testing。她說在 X 上看到 Cindy 的貼文：Cindy 原本不信任 agent，六個月後說自己每天 70% 的 token 花在驗證上。她說自己也差不多。逐字稿只有名字，有一份整理說這位是 @copyconstruct。這些技術都不新，以前是寫起來和維護起來都太貴。接回上篇 N-02
成果。團隊上個月上線約 11,000 個 PR，大約每天出一個穩定版。10 月有約 227 人貢獻過至少一個 PR，包括偶爾來一次的人。退回率穩定在 0.5% 左右。啟動和打字都比上市時快，開對話和切對話也是。她也承認 Electron 有它的天花板。
收尾。每次糾正 agent，先從改程式庫下手。先加 lint 擋住新的反模式，再清掉舊的，再把驗證做紮實。內圈還在產 slop 的話，自動化外圈只會產出更多 slop，還燒掉很貴的 token。地基打好之後，Grok Bot 現在每次發版都會自動開一個專案，像真的使用者一樣把整個 app 跑一遍，找到 bug 就開修正 PR，然後自動合併。她說大部分產品程式碼現在不經過深度的人工審查就進去了。
N-12 · 站得住的
糾正變成檢查，連顧舊系統的人都同意
她最核心的一招是「每次糾正 agent，就把它變成一條機器會執行的檢查」。這不是她一個人的主張。
Addy Osmani 9 月寫的〈Brownfield Agentic Engineering〉談的是舊系統，結論在這一點上跟她一樣：同一句審查意見第二次出現，就該寫成機器會執行的東西，像 lint 或測試，不要再寫成模型可能會忘的指示。機器強制的東西不用記得。
Vaibhav Gupta 在 AI Engineer World's Fair 的〈Fighting Slop with Slop〉做的是程式語言。他也用相依圖加 CI 檢查守住架構邊界，跟 Dune 擋 main 和 renderer 互相匯入是同一個做法。
「程式庫教壞 AI」這個說法也有別人講。Larridin 7 月的文章說，不一致的寫法和歷史包袱會被 AI 學走、大量複製。要注意 Larridin 自己在賣偵測 slop 的工具，文中的統計也是轉引的。
上篇的 Uncle Bob 是從另一條路走到這一招的。他先寫了 5 到 10 頁的 prompt，發現模型只把它當參考，才把規矩搬進事後跑的工具。接回上篇 N-03
