N-19 · 受校件
一個變更走的路
Claude Code 的程式碼大約九成由 Claude 撰寫，也由 Claude 審查。10 月那篇說，Anthropic 的 monorepo 每天進來的變更，從 5 月的 2,500 個左右，漲到 9 月超過 30,000 個。逐行人審已經做不到。
他們沒有拿掉審查，是把大部分的閱讀交給機器。目標寫得很具體：多數 PR 最多只經過一個人，這個人可以是作者自己，而且退回和事故不能變多。
    開 PR 之前
    1先驗過Claude 跑測試、build 和 linter。第二個 agent 在乾淨的 context 裡審 diff自動
    每個 PR
    2必過的 CI紅燈就擋住合併自動
    3Claude code review幾個 agent 平行找 bug，另一組投票，活下來的照嚴重度排自動
    4安全審查另外跑一次。沒解決的發現會擋住合併自動
    5照風險核准分類器定級：不用人，一個人，或兩個人人
    合併
    6merge queue套上變更以後，在最新的 main 上再跑一次自動
    合併以後
    7藏在 flag 後面，內部先用員工先跑過，才到所有人手上復原
    8分階段釋出先 latest，stable 跟在後面復原
    9盯著，往前修或退回作者和 on-call 一起看復原
  圖 2 · 依 10 月那篇的 Fig A 重繪 · 照原圖的分法，由人決定的只有第 5 步
第 5 步的分級有四條規矩：
  級別看變更本身，由分類器判，不看作者是誰。
  比較寬的路只給信得過的作者，多半是擁有那個 repo 的團隊。
  agent 的核准不算人的核准。叫 agent 寫這個變更的人，自己算一個審查者。
  核准只對某一個 commit 有效。程式碼再動，就要重新核准。
他們給的成績是 6 月到 9 月之間，合併的 PR 增加超過一倍，被退回的比例下降超過四成。這是相對降幅，文章沒有給原本的退回率。
N-20 · 校正
四個動作：隔開，考，記，修
11 月那篇的最後一段把做法收成四件事。檢查要放在被檢查的變更碰不到的地方。拿真正出過事的 bug 來考它。漏掉的要寫下來。寫下來的要修剪。我照這四件事整理兩篇的內容。
隔開：量具不能自己調刻度
  審查設定 REVIEW.md 只從 base branch 讀，PR 改不到它。
  審查結果綁在某一個 commit 上。有人在審的時候又 push，那次審查就不算。
  調 prompt 用的題，和最後考的題，分開放。
考：拿標準件來對
  ① 事故或退回弄壞東西的變更
  ② 專家確認bug 是什麼，在哪裡
  ③ 進題庫每次事故多一題
  ④ 改 reviewerprompt、工具或模型
  ⑤ 每天考一次每一題都算分
  ⑥ 分數有上升？有就留，沒有就丟
  右邊這一圈每改一次跑一次
圖 3 · 依 10 月那篇的 Fig C 重繪 · 點圖放大
題庫是過去出過事的 PR，由熟那段程式碼的工程師確認 bug 是什麼、在哪裡。每一題把 repo 還原到審查當時的狀態，配一句話的答案。reviewer 要說中那個 bug 才算分。
光考漏判不夠。一個什麼都報的 reviewer 也能考高分，所以他們另外拿合併後一直沒出事的變更給它審，看它會不會亂報。平常也統計作者怎麼回應每一則意見：修了，說它錯，說是故意的，或說不重要。
    原始發現幾個 agent 各自找到的
    驗證之後另一組 agent 投票留下的
    最後送出的審查作者真的看到的

記：漏掉的寫下來
  每個 commit 蓋上它是怎麼驗的。沒驗就寫 none，之後查得到。
  同一種漏網的問題，至少在兩個 PR 出現過，而且從 diff 看得出來，才列為候選規則。三個 agent 先試著推翻它，最後由人在 PR 裡核准。
  可靠性清單有 39 項，每一項都記著背後的事故。一個 diff 通常只對到 3 到 10 項。
修：壞掉的量具要報廢
  不穩的測試不准跳過，不准加 sleep，也不准重跑到過。找不到根因就刪掉，並寫下原因。
  測試、驗證步驟和規則檔都定期清。不清就只會一直長。
  recall 調到再進步就只是在背題為止。
四個動作講的是同一件事：檢查寫完不算數，每一道檢查都要有它自己的標準件。

比這四格更有用的，是他們自己寫出來的偏差。
  它一直在找舊 bug。他們對 reviewer 反覆報的東西跑 git blame，大約 59% 是它第一輪審的時候就在的程式碼。
  兩個 agent 會互相餵。有一個 CLI 的 PR，一個晚上審了又修五十多輪，作者才喊停。
  人自己把它弄糟。原文是「We made it worse ourselves」。他們習慣每個 PR 都多審幾輪。後來加了上限，審滿三輪，reviewer 會請作者退一步想做法。
  還沒有斷路器。退回或事故變多的時候，沒有東西會自動把核准收緊。工程師說要先有這個，才讓更多變更不經人就合併。
11 月那篇也留了一個口子。commit gate 在同一個 session 擋了兩次，第三次就放行，免得 Claude 卡死。文章給的理由是「Claude Code isn't perfect」。
兩篇加起來，做法寫得很細，最要緊的三個讀數沒有給：reviewer 最後的 recall，退回率的絕對值，事故的次數。
作者 Addy Osmani 9 月在自己的電子報裡補過兩個數字。工程師把 reviewer 的發現標成錯的，不到 1%。另一個是回頭分析：如果每個變更都過自動審查，過去 claude.ai 那些事故背後的 bug，大約三分之一會在上線前被抓到。這些 bug 當初多半過了仔細的人審，所以三分之一算多。可是也代表剩下大約三分之二，自動審查一樣抓不到。

N-23 · 上限
沒有不會偏的量具
阿里巴巴的 Qwen Team 6 月有一篇論文〈The Verification Horizon〉。它談的是訓練模型時拿什麼當獎勵，跟團隊怎麼審程式碼不是同一件事，但裡面有一張三角形很好用。論文說每一個驗證者都只是人的意圖的代理。意圖本來就寫不完整，而且一個指標只要被拿去最佳化，就不再是好指標。
  放得大
  貼近意圖
  不好鑽
  LLM 評審會被鑽
  單元測試只測到淺層
  人工審查放不大
  三樣都有的還沒有
圖 7 · 依論文前言整理 · 每一種訊號佔一條邊，只有兩端的性質 · 點圖放大
論文自己的實驗給了一個讀數。只拿測試當驗證的時候，有 28.57% 的題目是靠鑽漏洞過關的。加上品質評審和行為監控以後，降到 0.56%。這是訓練情境下的數字，搬到團隊的審查流程是我的延伸。
訓練以外的現場也有人講同一件事。同一場直播裡，Zechner 說太多人看到 agent 寫了一大堆 lint 規則和測試就放心。他的理由是 agent 還是會衝著目標鑽，不然就是量錯東西，或量得不夠。不清楚底下實際發生什麼，就不知道那些檢查值多少。他沒有因此說別做，原話是「anything is better than nothing」。他提醒的是另一件事：硬碟上多了一堆檢查，不等於它們證明了你以為的那件事。
Armin Ronacher 給了形式化驗證一個反例。他替 Pi 的一部分寫了 Lean 證明，寫完才問自己，要靠什麼機制讓原始碼一直跟證明對得上。照他到目前的經驗，證明多半變成 agent 可以讀的另一份產物，還綁不住 agent 接下來寫的程式。他相信這條路走得通，只是還沒看到一套從頭到尾順的做法。Zechner 補了一句：單一的純函式驗得了，整個系統驗不了，每個模組各自過關不代表合起來過關。下篇 N-11 記了 Lauren 用 Lean 抓到 bug。兩邊講的是不同的事，她說證明抓到了 bug，他說證明還管不住後面的變更。
這張三角形可以解釋，為什麼三篇的案例最後都長成三層：測試打底，中間一層機器審，最貴的人留到最後。沒有哪一條邊撐得住全部。
最後一把量具是人，人也會偏。Osmani 5 月寫過〈Cognitive Surrender〉，引的是華頓商學院 Shaw 和 Nave 的研究：1,372 個受試者，AI 給錯答案的時候，73% 的情況下人照收。更麻煩的是有 AI 在旁邊，人的信心反而變高。他形容自己掃過一個 600 行的 PR 就按核准：「You didn't review the code. You ratified it.」
9 月那篇他補了另一面。出事的時候挨罵的是按核准的那個人，可是速度和檢查都不是他定的。他的講法是「accountability needs authority」。
量具會偏，校正量具的人也會。差別在量具有履歷卡，人沒有。
N-24 · 貼標籤
能搬的五件事，和這份紀錄自己的偏差
  每次事故留一題。出事的那個 PR，加一句話寫清楚 bug 是什麼。這是最便宜的標準件，有十題就能開始考你的 reviewer。
  檢查的設定，放在被檢查的變更碰不到的地方。
  每個 commit 記下它是怎麼驗的。沒驗也照寫。
  退回率和事故率當護欄，不當成績。它們變高，代表人的時間只是從審查搬到善後。
  人審照變更的風險分級，不照作者。agent 的核准不算數。
不要搬的是九成和四成這兩個數字。它們沒有基準線，而且那個團隊做的產品就是 agent 自己，條件跟一般團隊不一樣。
這份紀錄自己的偏差
受校件的兩篇是廠商寫自己的產品，數字全是自報。作者 Addy Osmani 在 Anthropic 的 Claude Code 團隊工作，他 9 月那篇自己寫了他不中立。這份報告的初稿是用 Claude 寫的，跟受校件是同一家公司的模型。拿來比對的幾篇也都不是局外人：兩篇是公司部落格，論文來自另一家做模型的公司。v0.3 補的那場直播，兩位來賓做的是開源的 coding agent，不是模型廠商，立場離受校件比較遠。那一場我讀的是自動字幕，人名和術語有辨識錯誤，是照上下文還原的。
