選線的時候，先回答這七格
兩端是誰裝置對服務（很多、很弱、網路很爛）選 MQTT 這類面向裝置的協定；服務對服務選佇列或 log。Kafka 不是設計給大量不穩定 client 直連的。
沒人接時訊息要留 → 佇列線；不留也沒關係 → 廣播線。這是第一個、也是最重要的分岔。
讀過之後還要重讀（新服務補讀上週資料、邏輯寫錯要重算）→ log；讀完就算數 → work queue。
讀者幾個一個下游 → work queue 就夠；多個而且各自進度 → log；多個但只要當下 → 廣播。只有一個下游卻上 Kafka，通常是殺雞用牛刀。
誰負責重試中間人負責 → 佇列線；發送端負責 → 回撥線。回撥線的接收端一定要冪等。
時間窗秒 → 連線加廣播；分鐘 → 佇列加限速；小時 → 排程。時間窗拉寬一級，架構就便宜一級。
送還是握如果難的是「同時握住一百萬條連線」，那是連線層的問題（gateway 分片、心跳、重連風暴），跟 queue 無關。這格答錯，後面全部白做。
回答完這七格，再去看產品。多數時候答案會比想像中陽春：一台跑 Mosquitto 的機器、一張 Postgres 表、一個 cron。每多加一層 broker，就多一個半夜會叫你起床的東西，而且那個東西的授權條款可能明年就變了。
先問訊息沒人接時去哪裡，再問要不要留、要不要重讀。產品名稱是最後一格。
