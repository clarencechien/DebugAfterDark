「搜尋要快」是高熵句，「10 萬筆資料冷啟動，p95 < 200ms」是低熵句。任何 spec 都應該附三個具體例子，加 一個反例 （什麼情況該拒絕），反例的資訊量通常最大。這就是 Gherkin／ATDD 存在的深層理由：具體例子的熵遠低於形容詞。
C2 假設帳本（assumption ledger）
規定模型動工前先輸出「我替你做了哪些決定」。要它列的是它 替你填了什麼 ，它理解了什麼反而其次。填充從靜默變成顯式，你逐條打勾或打叉，直接攻擊「無接縫填空」這個機制。 本篇最後就附了一份 。
C3 Non-goals
一頁 PRD 有用，但要用對地方。它當不了完整的 spec，它是決策紀錄，資訊密度最高的欄位是「這次不做什麼」。正向需求有無限種寫法，負向約束一刀砍掉整個子空間。這跟依賴結構同構：都是約束，不靠偵測。
C4 原型與反應的迴圈
最誠實的一條：承認 spec 有一部分 只能被發現，沒辦法預先寫出 。看到會動的東西，才知道「不對，不是這個」。這算不上流程失敗，它就是量測行為本身，是 validation 唯一真正的儀器。AI 把單次修改的成本打到極低，正確的用法是更快丟出可以反應的版本，更密地採樣你自己的反應，花更久寫一份完美 spec 反而是誤用。
上游沒有測試，只有校準。 上游的工具是例子與反例、假設帳本和 non-goals，再加上原型與反應的迴圈。最後一項是 validation 唯一真正的儀器：有些 spec 只能被發現，沒辦法預先寫出。
