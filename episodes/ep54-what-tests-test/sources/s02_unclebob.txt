2026 年，寫了《Clean Code》、推了幾十年 TDD 的 Robert C. Martin 公開說，他不審查 agent 寫的程式碼。他改看測試覆蓋率和依賴結構，再加上圈複雜度、模組大小與變異測試，從指標推論品質，程式碼本身交給 AI。理由是人類讀 code 太慢，要生產力就得從 code 抽離，在更高的層次管理 [1] 。他的做法並沒有放手。他用單元測試和 Gherkin 測試把 agent 團團圍住，外面再加 QA 流程與品質指標，最後是變異測試和覆蓋率。產出必須跑完整條考驗關卡（gauntlet），他才信任 [2] 。他還描述過一條四段流水線，Specifier → Coder → Refactorer → Architect，每一段的人工介入遞減 [3] 。
三件事讓這不只是名人語錄。 一，他驗證驗證者 ：變異測試量的是你的測試有沒有牙齒，程式碼本身反而不是對象，這是大多數人的關卡裡缺的那一層。 二，他自己在往回修 ：7 月 2 日，比那則「一行都不讀」的貼文還早三週，他就說堆滿各種測試「能做不代表該做」，很多時候單元測試加 CRAP 評估就夠，大型專案才需要更多，而且他還在驗證中 [4] 。一個公開修正自己主張的人，比把它包裝成方法論來賣的轉述可信。 三，也最容易被聽錯：他證明的並非「不用讀 code」。 他能設計出那道關卡，靠的是 1970 年至今五十幾年的讀與寫。他示範的是判斷力的 再配置 ，從逐行審查搬到閘門設計，判斷力並沒有被 免除 。一個從沒讀過 code 的人，設計不出那道 gauntlet。
順帶一提，「人類讀 code 太慢所以跳過，生產力就回來了」，這本身是一個沒被量測的宣稱。他感覺快了。 上篇 那批資深工程師也感覺快了 20%，實測卻慢了 19%。


【EP42〈Clean Code 的作者不讀 AI 的程式碼，那他讀什麼？〉的稿子】
先看第一件事：他說不讀的，是哪幾樣。在同一串回覆裡，他把分工講得很細。實作程式碼跟單元測試，都是 agent 寫，這兩樣他不看。驗收測試跟 QA 程序，也是 agent 起草，可是他會看。重要的細讀，剩下的抽查。他的驗收測試用一種叫 Gherkin 的格式寫。每一條都寫成，在什麼情況下，做了什麼，應該看到什麼。人讀得懂，工具也能把它轉成測試來跑。最後，產品實際跑起來的樣子，他會定期自己手動測一次。所以說他不讀 code 了，其實不太準。比較準的說法是：他不讀實作，改讀規格。
那研究怎麼說？這份報告整理了今年的四篇論文。合起來只支持一件事：一行一行的人工檢查，不該是唯一的關卡。可是可不可以完全不讀？目前的證據還不支持。其中一篇看了四百多個 repo，有把 AI 設定檔放進去的，程式變複雜的幅度比較小，作者自己說這還只是假說。這張卡也有幾個地方沒蓋到章。這是一個人自己的專案，一個遊戲，沒有團隊，也沒有上線以後的缺陷率。規格也是 agent 起草的，第一站寫錯，後面四站會一路蓋章過去。新人怎麼養成，他說他沒有完美的答案。還有責任：只有人能替 agent 的產出負責。卡上的章再齊，簽名的還是人。
好，今晚的 breakpoint。第一，Uncle Bob 沒有不讀。他不讀實作和單元測試，改讀規格，再看分數和架構圖。第二，很長的 prompt 守不住規矩，他把規矩搬進事後跑的工具，因為工具不會被說服。第三，流程卡只能證明每一站都蓋了章。章蓋得對不對，要看第一站的規格，有沒有人認真讀。原文連結在節目資訊欄。我是 Ping，有收到的話，回我一個 pong。下次見。
